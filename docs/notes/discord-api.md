# Discord API facts for the phase 1 driver

The phase 1 Discord driver ([design, section 5.2](../design/overview.md#52-chat-front-end-and-surface-driver), [section 8](../design/overview.md#phase-1-replace-c-lord-for-dispatched-orders-discord-and-claude-code)) is to be written against the facts below, not from memory.

Checked on 2026-11-17. The documentation was read in [discord/discord-api-docs](https://github.com/discord/discord-api-docs) at commit [`14b3a42`](https://github.com/discord/discord-api-docs/tree/14b3a42df7377b492d15af176a4c556497b00156), the source of discord.com/developers/docs. Each answer links the published page.

How each answer is marked:

- **docs**: taken from Discord's documentation, quoted or closely paraphrased, with a link.
- **checked**: verified by a run. For the library this was a build, or a read of the library's source at the stated tag. No answer here was checked by a run against Discord itself. That needs a test application and server, and the captures belong to the driver's issue.
- **unverified**: the documentation does not say, or says it only indirectly. The driver must not depend on it until a capture confirms it.

## 1. Go library

**Use [github.com/disgoorg/disgo](https://github.com/disgoorg/disgo), pinned to an exact version.** Keep its types inside the driver package.

| | disgoorg/disgo | bwmarrin/discordgo | diamondburned/arikawa/v3 |
|---|---|---|---|
| Latest release (module proxy) | v0.20.0, 2026-11-06 | v0.29.0, 2025-05-24 | v3.6.0, 2025-09-04 |
| API version it targets | 10 (`rest.Version`, `gateway.Version`) | 9 (`APIVersion = "9"`) | not checked |
| `nonce` + `enforce_nonce` on Create Message | yes (`MessageCreate.Nonce`, `EnforceNonce`) | no (`MessageSend` has neither) | not checked |
| Rate limits | keyed by `X-RateLimit-Bucket`, also reads `X-RateLimit-Global` and `Retry-After` | own buckets keyed by route, does not read `X-RateLimit-Bucket` | not checked |
| Start thread from message | `rest.CreateThreadFromMessage` | `Session.MessageThreadStart` | not checked |
| Listed by Discord | no | yes, the only Go library on [Community Resources](https://discord.com/developers/docs/developer-tools/community-resources#libraries) | no |

Marked **checked**. Release dates come from `https://proxy.golang.org/<module>/@latest` ([disgo](https://proxy.golang.org/github.com/disgoorg/disgo/@latest), [discordgo](https://proxy.golang.org/github.com/bwmarrin/discordgo/@latest), [arikawa](https://proxy.golang.org/github.com/diamondburned/arikawa/v3/@latest)). The rows on API version, nonce, rate limits and threads come from reading each library's source at the tag shown. A program that imports `disgo`, `disgo/bot` and `disgo/gateway` with the four intents of section 6 builds with `CGO_ENABLED=0` for linux/amd64 and darwin/arm64 (go1.27.4). `godave` is in its dependency graph, but it does not need cgo for that build.

Why not discordgo: it has had no release in eighteen months, it targets API v9, and it cannot send `enforce_nonce`, the one way to make a post idempotent (section 4). Its rate limiter does not key on the bucket header that Discord says to use (section 5).

What disgo does not cover, or where the driver must be careful:

- It is still at v0.x, and minor releases break the API. Pin the version and upgrade on purpose.
- It does not split long text, choose between buttons and menus, or keep an outbox. Those belong to the driver and the chat front end anyway (design 5.2).
- Discord does not vouch for it. Discord's list says only that the libraries on it "have valid rate limit implementations, are recently maintained, and have large communities of active bots", and disgo is not on it.

## 2. Webhook, bot or person

From the [message object](https://discord.com/developers/docs/resources/message#message-object) (**docs**):

| Sender | How to tell |
|---|---|
| A webhook | `webhook_id` is present. |
| A bot account | `webhook_id` is absent and `author.bot` is `true`. |
| A person | `webhook_id` is absent, and `author.bot` and `author.system` are absent or `false`. |

- `webhook_id`: "if the message is generated by a webhook, this is the webhook's id".
- `author`: "only a valid user in the case where the message is generated by a user or bot user. If the message is generated by a webhook, the author object corresponds to the webhook's id, username, and avatar. You can tell if a message is generated by a webhook by checking for the `webhook_id` on the message object." So `author.id` of a webhook message is not a user id, and `author.username` is whatever the poster chose for that message. Never authorise on either.
- `author.bot`: "whether the user belongs to an OAuth2 application". `author.system`: "whether the user is an Official Discord System user" ([user object](https://discord.com/developers/docs/resources/user#user-object)).
- `application_id`: "if the message is an Interaction or application-owned webhook, this is the id of the application" (**docs**).

What the driver does with this:

- **Allow a webhook by `webhook_id`.** The webhook's `id` is its snowflake, and the same id is in its execute URL `POST /webhooks/{webhook.id}/{webhook.token}` ([execute webhook](https://discord.com/developers/docs/resources/webhook#execute-webhook)). It is fixed for the webhook's lifetime, and a deleted and recreated webhook gets a new id. **unverified** as a sentence: the documentation never says it in so many words. It follows from the id being the resource's snowflake.
- **Allow the owner by `author.id`, only when `webhook_id` is absent.**
- **Ignore the bot's own messages** by comparing `author.id` with the bot's user id, which is in the gateway `READY` event.
- **unverified**: whether the author object of a webhook message also carries `bot: true`. Argon said it does "in practice", but the documentation lists only `id`, `username` and `avatar`. Check `webhook_id` first, so the answer does not matter.

## 3. Threads started from a channel message

From [Start Thread from Message](https://discord.com/developers/docs/resources/channel#start-thread-from-message), [threads](https://discord.com/developers/docs/topics/threads) and [message reference](https://discord.com/developers/docs/resources/message#message-reference-content-attribution-thread-starter-messages) (**docs**):

- "The id of the created thread will be the same as the id of the source message, and as such a message can only have a single thread created from it." The source message gets the `HAS_THREAD` flag (`1 << 5`). The call fires Thread Create and a Message Update for the source message.
- The thread's first message is a `THREAD_STARTER_MESSAGE` (type 21). It is not deletable ([message types](https://discord.com/developers/docs/resources/message#message-object-message-types)). It "will never have content, embeds, or attachments, mainly just the `message_reference` and `referenced_message` fields". The reference points at the channel message.
- **Deleting the channel message does not delete the thread.** "Public threads must be created from an existing message, but can be 'orphaned' if that message is deleted" ([threads](https://discord.com/developers/docs/topics/threads)). The starter message stays. Its `referenced_message` is then `null`: "If the field exists but is null, the referenced message was deleted" ([message object, note 4](https://discord.com/developers/docs/resources/message#message-object)).
- **Editing the channel message** fires a Message Update in the parent channel only. Nothing in the thread is stored with the old text, because the starter message holds no content of its own. **unverified**: whether a client then shows the new text at the top of the thread (very likely, since the starter only points at the message), and whether any event is sent for the thread.

What the driver does with this: the thread must not depend on the channel message. Phase 1 requires that "the full prompt is in the thread, and editing the channel message afterwards changes nothing". So the driver reads the trigger once, from the Message Create, and posts the full prompt into the thread as its own message. It ignores later Message Update events for trigger messages. The thread id can be computed before the thread exists, because it equals the trigger message's id.

## 4. Idempotency key

From [Create Message](https://discord.com/developers/docs/resources/message#create-message) and the [change log of 2024-02-12](https://discord.com/developers/docs/change-log#enforced-nonces-on-create-message-endpoint) (**docs**):

- `nonce` (integer or string, "up to 25 characters") comes back in the Message Create event. On its own it deduplicates nothing.
- With `enforce_nonce: true`: "it will be checked for uniqueness in the past few minutes. If another message was created by the same author with the same nonce, that message will be returned and no new message will be created."
- **How long: "a few minutes", no exact figure.** The status code of a deduplicated response is not documented either (**unverified**).
- **Execute Webhook takes no nonce.** `nonce` and `enforce_nonce` are not in its [parameters](https://discord.com/developers/docs/resources/webhook#execute-webhook). This concerns the manager's posts, not the driver's.
- Posting into a thread is the same Create Message call on the thread's id, so `enforce_nonce` works there.
- There is no `Idempotency-Key` header or other mechanism in the documentation.

What the driver does with this: send the outbox key (`Post`'s `key`, hashed or cut to 25 characters) as `nonce` with `enforce_nonce: true`. This only protects a retry made within minutes. The outbox must still record the returned message id before it marks a post done. After a longer outage it must look in the thread's history (`Since`) for a message that carries its nonce before it posts again. Section 5 has the history limits. **unverified**: whether `nonce` is returned when history is fetched later. The documentation mentions it only for the Message Create event.

## 5. Limits

All **docs**. Discord says limits "should not be hard coded into your app" ([rate limits](https://discord.com/developers/docs/topics/rate-limits)). The driver puts these figures in `Limits()` and treats a 400 or 429 as the final word.

| Limit | Value | Source |
|---|---|---|
| Message content | 2000 characters, on create and edit | [Create Message](https://discord.com/developers/docs/resources/message#create-message-jsonform-params) |
| Embeds | up to 10, 6000 characters in total | same |
| Attachments per message | 10 (error 30015, "Maximum number of attachments in a message reached (10)") | [JSON error codes](https://discord.com/developers/docs/topics/opcodes-and-status-codes#json) |
| Size of one file | 20 MiB by default; more only through the uploader's Nitro or the server's boost tier | [Uploading Files](https://discord.com/developers/docs/reference#uploading-files) |
| Size of one request | 25 MiB | [Create Message, limitations](https://discord.com/developers/docs/resources/message#create-message) |
| History page | `limit` 1 to 100, default 50; `before`, `after` and `around` are mutually exclusive; results come newest first | [Get Channel Messages](https://discord.com/developers/docs/resources/message#get-channel-messages) |
| Thread name | 1 to 100 characters | [Start Thread from Message](https://discord.com/developers/docs/resources/channel#start-thread-from-message) |
| Initial reply to a button press | within 3 seconds; the interaction token is valid for 15 minutes | [Receiving and responding](https://discord.com/developers/docs/interactions/receiving-and-responding) |

**unverified**: whether "2000 characters" counts Unicode code points or UTF-16 units. Split on code points with a safety margin until a capture shows the difference.

How rate limits are reported, per route ([rate limits](https://discord.com/developers/docs/topics/rate-limits), **docs**):

- Each response may carry `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (epoch seconds), `X-RateLimit-Reset-After` (seconds, with decimals) and `X-RateLimit-Bucket`. A 429 also carries `X-RateLimit-Global` (only for the global limit), `X-RateLimit-Scope` (`user`, `global` or `shared`) and `Retry-After`.
- Similar endpoints may share a limit, which the bucket header shows. Discord recommends using the header "as a unique identifier for a rate limit". The limit is counted separately per top-level resource in the path: `channel_id`, `guild_id`, or `webhook_id` (+ token). So the true key is the bucket together with the channel.
- The body of a 429 has `message`, `retry_after` (float seconds), `global` (bool) and optionally `code`. Wait for `Retry-After` or `retry_after`.
- The global limit is 50 requests per second per bot. Interaction endpoints are exempt.
- Invalid requests: 10,000 responses with status 401, 403 or 429 per 10 minutes, per IP address, lead to a temporary ban. A 429 with scope `shared` does not count. The driver must stop after a 401 (the token is bad). It must not retry a 403.
- Gateway: 120 events sent per connection per 60 seconds ([gateway](https://discord.com/developers/docs/events/gateway#rate-limiting)).

## 6. Intents and permissions for phase 1

What phase 1 does on Discord:

- receive a trigger posted by a webhook in an enabled channel, and follow-ups from the webhook and the owner in the thread;
- start a public thread from the trigger;
- post, edit and delete its own messages there, with files;
- read history after an outage;
- open a direct message with the owner, post one message with one button there, take the button press, and read the owner's replies.

Phase 1 does not rename threads after creating them, archive them, react to messages (no lamps), or post in the parent channel.

### Gateway intents

From [list of intents](https://discord.com/developers/docs/events/gateway#list-of-intents) and [message content intent](https://discord.com/developers/docs/events/gateway#message-content-intent) (**docs**):

| Intent | Bit | Privileged | Why |
|---|---|---|---|
| `GUILD_MESSAGES` | `1 << 9` | no | Message Create in channels and threads. |
| `MESSAGE_CONTENT` | `1 << 15` | **yes** | Without it, `content`, `embeds`, `attachments` and `components` are empty in guild messages, except when the bot is mentioned. Webhook triggers do not mention the bot. It must be switched on for the application in the Developer Portal. |
| `DIRECT_MESSAGES` | `1 << 12` | no | Message Create for the owner's replies in the direct message. Content in direct messages arrives without `MESSAGE_CONTENT`. |
| `GUILDS` | `1 << 0` | no | Thread Create, Update and Delete, and the active threads in Guild Create. |

The button press (Interaction Create) needs no intent: "Any events *not* listed means it's not associated with an intent and will always be sent to your app."

**unverified** for `GUILDS`: the driver may manage without it, since it learns its threads from its own API calls and the database. Argon proposed dropping it. It is kept because it is not privileged and costs nothing. Without it the driver would not see a thread of its own archived or deleted by someone else, and disgo's cache would hold no channels. If "no more" must be read strictly, drop it and check by a run that nothing breaks.

### Channel permissions

These are granted on the enabled channels. Threads inherit them, except that "The `SEND_MESSAGES` permission has no effect in threads; users must have `SEND_MESSAGES_IN_THREADS`" ([threads, permissions](https://discord.com/developers/docs/topics/threads#permissions)). Bits are from [permission flags](https://discord.com/developers/docs/topics/permissions#permissions-bitwise-permission-flags) (**docs**).

| Permission | Bit | Why |
|---|---|---|
| `VIEW_CHANNEL` | `1 << 10` (`0x400`) | See the channel and its threads. Without it there are no events for them. |
| `READ_MESSAGE_HISTORY` | `1 << 16` (`0x10000`) | `Since` after an outage. "If the current user is missing the `READ_MESSAGE_HISTORY` permission in the channel, then no messages will be returned." |
| `CREATE_PUBLIC_THREADS` | `1 << 35` (`0x800000000`) | Start a thread from the trigger. |
| `SEND_MESSAGES_IN_THREADS` | `1 << 38` (`0x4000000000`) | Post in the thread. |
| `ATTACH_FILES` | `1 << 15` (`0x8000`) | Files the agent hands over. |

Needed for none of phase 1:

- Editing or deleting the bot's own messages. Only messages of other users need `MANAGE_MESSAGES` ([Edit Message](https://discord.com/developers/docs/resources/message#edit-message), [Delete Message](https://discord.com/developers/docs/resources/message#delete-message)).
- Opening a direct message ([Create DM](https://discord.com/developers/docs/resources/user#create-dm)) and posting a button in it. Channel permissions are guild permissions.
- **unverified**: `SEND_MESSAGES`. Phase 1 never posts in the parent channel, and Start Thread from Message names no permission besides the thread ones. Check by a run that a thread can be started without it.
- **unverified**: whether a direct message can be opened with a user who shares no server with the bot. The documentation does not say. In phase 1 the owner is in the server, so this does not arise.

For later phases (not phase 1):

- Renaming or archiving a thread. The [threads page](https://discord.com/developers/docs/topics/threads#editing--deleting-threads) says it "requires `MANAGE_THREADS` or that the current user is the thread creator". The [Modify Channel](https://discord.com/developers/docs/resources/channel#modify-channel-json-params-thread) page names only `MANAGE_THREADS` (and `SEND_MESSAGES` to unarchive). The two pages disagree, so this is **unverified** until a run.
- Lamps as reactions need `ADD_REACTIONS` (`1 << 6`). The `GUILD_MESSAGE_REACTIONS` intent is needed only to read reactions.

## 7. The layout: channels, categories and active threads (#599)

Checked on 2026-11-23, in [discord/discord-api-docs](https://github.com/discord/discord-api-docs) at commit [`9b737ec`](https://github.com/discord/discord-api-docs/tree/9b737ec51ee8d5076af0565d209a9adf8f590a27). Marked as in the sections above.

**The gateway sends the whole layout; no REST request is needed** (**docs**):

- [Guild Create](https://discord.com/developers/docs/events/gateway-events#guild-create) carries `channels`, "Channels in the guild", and `threads`, "All active threads in the guild that current user has permission to view". It is sent for each server after `READY`, when a server becomes available again, and when the bot joins one. An unavailable server comes as an unavailable guild object, and [Guild Delete](https://discord.com/developers/docs/events/gateway-events#guild-delete) with `unavailable` says a server became unavailable.
- [Channel Create, Update and Delete](https://discord.com/developers/docs/events/gateway-events#channel-create) carry a channel object. Channel Update "is not sent when the field `last_message_id` is altered".
- [Thread Create, Update and Delete](https://discord.com/developers/docs/events/gateway-events#thread-create): Create and Update carry the whole thread; Delete carries only `id`, `guild_id`, `parent_id` and `type`. Unarchiving sends a Thread Update with the full channel object ([threads, unarchiving](https://discord.com/developers/docs/topics/threads#unarchiving-a-thread)).
- [Thread List Sync](https://discord.com/developers/docs/events/gateway-events#thread-list-sync) is "sent when the current user gains access to a channel", with all active threads of `channel_ids`; "If omitted, then threads were synced for the entire guild. This array may contain channel_ids that have no active threads as well, so you know to clear that data."
- All of these come with the `GUILDS` intent, which the driver already asks for (section 6).
- The [threads page](https://discord.com/developers/docs/topics/threads#gateway-events): "the gateway protocol is designed to ensure that bots are able to have an accurate view of the full set of active threads, but archived threads are not synced up-front via the gateway"; "Clients will not be informed of a thread through the gateway if they do not have permission to view that thread". On losing access to a channel, no Thread Delete is sent; the event that changed the permission is.

**Channels the bot may not view** ([obfuscated channels](https://discord.com/developers/docs/resources/channel#channel-object-obfuscated-channels), [change log of 2026-11-16](https://discord.com/developers/docs/change-log), **docs**): since 2026-11-16, for every bot, such a channel still comes over the gateway, in Guild Create and in the channel events, but obfuscated: "check whether its `flags` field has the `CHANNEL_OBFUSCATED` channel flag (`1 << 17`) set. Do not rely on inspecting `name`". "`id`, `type`, `position`, and `parent_id` will not be obfuscated". "Channel categories are viewable if any of their child channels are viewable." Regaining access sends a Channel Update with the full channel, for its category too. Over HTTP, [Get Guild Channels](https://discord.com/developers/docs/resources/guild#get-guild-channels) omits such channels.

**Order** (**docs**, except where marked):

- A channel's `position` is its "sorting position" and "channels with the same position are sorted by id"; a channel's `parent_id` is its category, and a category holds at most 50 channels ([channel object](https://discord.com/developers/docs/resources/channel#channel-object)).
- [List Active Guild Threads](https://discord.com/developers/docs/resources/guild#list-active-guild-threads): "Threads are ordered by their `id`, in descending order." The driver orders a channel's active threads that way, the newest first.
- **unverified**: that Discord's client shows the channels in no category first, and in a category the text channels before the voice and stage channels, each by position. The documentation does not say how the client lays them out; the driver does so until a capture of a server checks it (#613).
- **unverified** as a format: a link that opens a channel or a thread in the client, `https://discord.com/channels/<guild>/<channel>`. The documentation shows it only in examples (a tutorial: "if my URL was `https://discord.com/channels/123456/789101112`, the Guild ID is the first number"; the change log links its own channels so). A thread is a channel, so its id goes in the same place.

**Rate limits** ([rate limits](https://discord.com/developers/docs/topics/rate-limits), **docs**): REST limits are per route and per top-level resource (`/guilds/{guild.id}/channels` counts against its `guild_id`), plus the global 50 requests per second; Discord says limits "should not be hard coded" and are read from the response headers (section 5). Keeping the layout from the gateway makes no request at all, so it adds nothing to either limit, however often channels and threads change. The only gateway limit is on what a client sends (120 per 60 seconds), and the layout sends nothing. Polling [Get Guild Channels](https://discord.com/developers/docs/resources/guild#get-guild-channels) and [List Active Guild Threads](https://discord.com/developers/docs/resources/guild#list-active-guild-threads) was the alternative, and is not needed.

**Captures**: `testdata/v10` has a channel object, threads, a thread renamed and a thread archived, all used by the layout's test. Guild Create, the channel events, Thread Delete, Thread List Sync and an obfuscated channel have no capture yet (#613).

## 8. Mentions, replies and forwards: what is a call (#869)

Checked on 2026-11-25, in [discord/discord-api-docs](https://github.com/discord/discord-api-docs) at commit [`9b737ec`](https://github.com/discord/discord-api-docs/tree/9b737ec51ee8d5076af0565d209a9adf8f590a27). Marked as in the sections above.

From the [message object](https://discord.com/developers/docs/resources/message#message-object) (**docs**):

- `mentions`: "users specifically mentioned in the message". `mention_roles`: "roles specifically mentioned in this message", as ids. `mention_everyone`: "whether this message mentions everyone"; `@here` has no field of its own.
- A reply is `type` 19 and carries `message_reference` of `type` 0; a forward carries `message_reference` of `type` 1 and `message_snapshots`, whose messages have no author. A message of type 21 (a thread's starter) carries `referenced_message` too, and is nobody's reply.
- `referenced_message`: "If the message is one of these but the `referenced_message` field is not present, the backend did not attempt to fetch the message that was being replied to, so its state is unknown. If the field exists but is null, the referenced message was deleted."
- `edited_timestamp`: "when this message was edited (or null if never)". So a catch-up can tell an edited message, though not what it said before.

The role of a bot ([role object](https://discord.com/developers/docs/topics/permissions#role-object), **docs**): `managed`, "whether this role is managed by an integration", and `tags.bot_id`, "the id of the bot this role belongs to". The roles come with the gateway's Guild Create, and one at a time with Guild Role Create and Guild Role Update, all with the `GUILDS` intent; no REST request is needed.

**unverified**, until a capture checks them (`testdata/README.md`, "Calls"):

- whether `mentions` and `mention_roles` list a mention that stands in a quote or in code. The driver does not rely on it: a mention is the message's own only when the service lists it and the text has it outside quotes and code.
- which texts Discord's client shows as a quote or as code; the documentation does not say. The driver leaves out what it may show so: a line that begins with `>`, with or without a space after it or before it, also in a list or a heading; all that follows `>>>`; code between backticks and in blocks, also a block left open, and also one that opens on a line that may be a quote. It errs to "no call". It does not tell a backtick in a link or in bold text from one that opens code.
- whether a reply's ping is in `mentions` when the mention is switched off in the client. The driver does not read the ping: it goes by the replied-to post's author.

## Where the answers came from

Argon (Antigravity CLI, `agy -p`) was asked one question per section. Every claim kept here was checked against the documentation at the commit above, or against the libraries' tags. Corrections to Argon's answers:

- It gave disgo's latest release as v0.19.6 of June 2026. The module proxy has v0.20.0 of 2026-11-06.
- It said discordgo handles rate-limit buckets. It does, but it keys them by route and ignores `X-RateLimit-Bucket`.
- It said the documentation does not state the limit of 10 attachments. Error code 30015 does.
- It quoted a sentence about gateway events in threads ("to anyone who can view the thread") that is not in the documentation. Several of its rate-limit quotes were paraphrases. The quotes in this note are from the source.
